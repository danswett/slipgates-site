Privacy for the Slipgates beta

Beta

Slipgates is operated by Dan Swett, an individual. The beta is for invited adults in the United States only. Invitations are currently on hold. Real reports must not be sent through the in-app or staging feedback service while real-report collection and processing remain uncleared. You can still send privacy questions to support@slipgates.com.

The operating details below are based on the November 7 deployed-build and settings reviews, plus the confirmed support contact and report-preview behavior. Those reviews are not an independent audit. Some client, provider and deletion details are still being confirmed and are identified below. This notice does not promise anonymous use, US-only processing, no retained copies or deletion of everything within 30 days.

Hosting and GitHub sign-in

Use and providers: The web application is configured for GitHub Pages. The production relay uses GitHub device-flow sign-in, receives the device-flow/token responses, obtains your numeric GitHub account ID and login, and issues a Slipgates account token containing the account ID, login and expiry. The actual hosting/proxy path for this website, Cloudflare's role and the full visitor-data handling have not yet been confirmed; an app-hosting configuration is not proof of this website's served content or provider behavior.

Location and access: The reviewed relay compute is in Azure West US 2, United States. GitHub/Cloudflare processing locations, visitor-data categories and provider/administrative access roles have not yet been confirmed.

Retention and requests: The Slipgates account token is valid for 30 days; that is not a 30-day deletion promise. The deployed relay application-code review found GitHub tokens handled in memory during sign-in, not stored or logged by that application code. Automatic GitHub-token revocation was not configured according to the settings review. You can revoke the application's authorization in GitHub; that is different from deleting Slipgates account records. Client-side token storage, provider records/copies and their retention and deletion procedures have not yet been confirmed.

Account and device records

Use and providers: Azure Blob Storage holds a roster for your account with machine ID, name, kind (host) and last-seen time, plus recently forgotten machine IDs and times. The reviewed implementation supports up to 64 machines.

Location and access: The identified storage and relay compute are in Azure West US 2. The relay deployer's review reports account-scoped presence access for that account's signed-in devices. Azure service identities and operators also have administrative access paths. The complete effective reader-role set and processing outside the identified regional resources have not yet been confirmed.

Retention and requests: Roster expiry is configured after 180 days untouched. Soft delete, versioning and change feed are off in the reviewed account. Regional replication is not an absence of copies; other provider/downstream copies have not yet been confirmed. Forgetting a machine is not account erasure, and recently forgotten IDs/times remain in the roster. There is no relay account-erasure feature. A documented, accepted manual account-purge procedure has not yet been confirmed; contact the privacy address for requests.

Session delivery and content

Use and providers: Slipgates forwards session information, including prompts, replies and approvals, between the PC and devices connected to the account through the Azure relay. A review of the deployed relay code found socket-to-socket forwarding and no normal-frame persistence path in that code; the separate temporary-transfer path is described below.

Location and access: The reviewed relay is in Azure West US 2. The deployer reports routing to the account's connected devices. Client encryption, actual key holders and endpoint access, and end-to-end content transit/processing locations have not yet been confirmed for this notice. We are not making an end-to-end-encryption or relay-unreadability guarantee on that evidence alone.

Retention and requests: Normal frames are forwarded through process memory according to the code review, but actual memory/crash-dump handling and client/device copies, backups and retention have not yet been confirmed. Connection records have the separate retention periods below. A confirmed content-access/deletion procedure covering endpoints and remaining provider copies is not yet available; uninstalling or closing a connection must not be treated as erasing every copy.

Connection, fault and security records

Use and providers: The reviewed relay application logs connection tag, device kind, duration, frame/byte counts, sign-in completion/counters, and push host/status/byte counts, rather than normal message content in those identified logging statements. The monitoring services are Azure Container Apps, Log Analytics and Application Insights. The complete set of automatically collected fields, including any URLs, identifiers, IP information or payload data captured elsewhere, has not yet been confirmed. This is not a "no identifiers," "no IPs" or "nothing logged" promise.

Location and access: The identified compute and monitoring resources are in Azure West US 2. The subscription review reported a human Owner and relay-deployment identities; it did not establish the complete telemetry reader set or inherited/provider access. Processing outside the identified resources remains unconfirmed.

Retention and requests: Log Analytics is configured for 30 days and Application Insights for 90 days. Default Application Insights IP masking was reported; it does not prove that no IP is received or recorded elsewhere. Other copies and provider residuals are unconfirmed. No per-person telemetry deletion procedure is currently established in the supplied operational record. The privacy contact coordinates requests; scheduled ageing is not proof of request-based or all-copy erasure.

Temporary transfers and push notifications

Use and providers: Temporary transfers use Azure Blob Storage. The deployed-relay review describes receiving client-encrypted blobs; actual client encryption and key handling still need client-side confirmation. The configured web-push path signs and forwards notifications and handles the push endpoint, size and time. Depending on browser or operating system, its allowed delivery services include Apple web push, Google FCM, Mozilla and Microsoft Windows notifications. This allow-list does not establish which vendors have actually been used. Client-side push encryption, endpoint ownership and additional recipient restrictions remain unconfirmed.

Location and access: The reviewed blob storage is in Azure West US 2. Extra-regional processing and push-provider locations/access have not yet been confirmed. The deployer reports HTTPS user-delegation links scoped to one blob and permission: upload/read links last 30 minutes and a transfer ticket lasts 24 hours. Do not share transfer links; further sharing/recipient enforcement and effective storage permissions remain unconfirmed.

Retention and requests: The temporary blobs/ prefix is configured for lifecycle deletion one day after creation. Soft delete and versioning are off in the reviewed storage; other copies remain unconfirmed. Push TTL is capped at 24 hours in the reviewed path, not a promise that every vendor copy is erased then. Link expiry is not data deletion. Effective manual blob-delete authorization, per-user deletion procedures and push/provider deletion limits have not yet been confirmed.

Support email and privacy requests

Beta support is by email only. Send only the minimum needed. Do not post support content or personal information in public GitHub issues. Screenshots, logs and attachments can contain names, paths, prompts, code, tokens or other private information; check them before sharing.

The confirmed contact for beta support and privacy requests is support@slipgates.com. Cloudflare Email Routing forwards messages sent there to the operator's personal email inbox. The destination inbox provider, other authorized reader/forwarding roles, and the receiving inbox's retention and deletion limits are not yet confirmed. Do not assume that only the operator can technically access every copy or that support messages are automatically deleted within 30 days.

The owner has confirmed:

support@slipgates.com is live and receives mail. I, Dan Swett, check it each business day, arrange authorized coverage when away, aim to acknowledge privacy requests within three business days, and own triage and coordination with the relevant service operators for access, correction and deletion requests, subject to applicable law and the disclosed retention/provider limits.

The acknowledgement is an operational aim, not a legal response deadline or a promise to complete a request or erase data within three days. Requests will be handled as required by applicable law. Request coordination does not itself establish each service's ability or procedure to delete records.

Deletion and revoking access

The beta does not offer an account-erasure feature or promise manual deletion. Roster records have a configured expiry after 180 days untouched. Log Analytics is configured for 30 days and Application Insights for 90 days. Temporary transfer blobs have lifecycle deletion configured one day after creation. These are the specified schedules, not a guarantee of erasure from every copy; support-mail and other provider-copy retention are not yet fully confirmed.

You can revoke Slipgates' authorization in GitHub. That does not delete Slipgates records or guarantee immediate invalidation of already-issued Slipgates account tokens. For privacy questions or requests, email support@slipgates.com. The privacy address still receives and answers requests as required by applicable law. This description does not waive rights or duties that applicable law imposes.

In-app feedback, the preview and the redactor

The reviewed production relay has feedback uploads disabled: the reviewed deployed build has no feedback upload route and no feedback settings. The staging service can accept uploads from signed-in accounts and does not itself enforce the synthetic-only rule. Staging is for instructed synthetic testing, not real reports; do not submit real reports there. Client endpoint selection and enforcement of the current hold still need confirmation. A report-builder or preview screen is not permission to send real data while that hold applies.

The client includes a report preview before choosing Send. The redactor removes values from recognized password, token and similar named fields. It does not catch secrets without a recognized name, and other sensitive information can remain. Check the preview: it shows the report content you would send. Do not choose Send if it includes anything you do not want to share. Redaction is not a guarantee that a report, screenshot, log or attachment contains no sensitive information.

The provisioned production feedback storage and identified vault/audit resources are in Azure West US 2; the reviewed staging storage and relay are also in West US 2. The provisioned relay feedback identity has create-only access, not read/list/delete. The worker identity has container-scoped Blob Data Reader and Secrets User access to the dedicated vault. These grants do not establish complete custodian isolation or every inherited/provider access path.

The production ciphertext container has a locked 30-day minimum hold and lifecycle deletion configured for day 31 after creation; deletion is not available during the minimum hold, and lifecycle configuration is not proof of erasure from every copy. Staging's 30-day policy is not locked. The reviewed production and staging feedback accounts have blob/container soft delete and versioning off. The configured feedback read-audit period is 30 days; the credential vault has 90-day secret soft delete and purge protection. Credential and audit schedules are not report-content deadlines.

Planned automated feedback handling would decrypt reports for authorized feedback staff and store plaintext in private GitHub issues. The approved design gives the supervising AI service status only, not report plaintext or keys; this isolation is not yet proven in a ready production worker. Real-report processing is not cleared. The adopted policy is to remove active plaintext within 30 days of the original server-recorded upload time, earlier for actionable requests; implementation and complete deletion/replay suppression are not yet proven. Actual worker/App/key-custody readiness, GitHub readers/integrations/copies and locations, receipt/failure/private-copy schedules, and the complete deletion procedure/provider residuals remain unconfirmed. No configured backup is not a guarantee of no copies.

The in-app warning reads:

Check the preview. The redactor removes values from recognized password, token and similar named fields; secrets without a recognized name and other sensitive information may remain. The preview shows the report content you would send. Do not choose Send if it includes anything you do not want to share.

While the real-report hold remains, it also states:

Real reports are not open for submission. Do not send real session content or personal information through this feedback path. Only explicitly instructed synthetic testing is permitted.

Optional automatic diagnostics

Optional automatic diagnostics are not enabled in this beta and cannot be turned on yet. Their design excludes session content; they must pass technical and privacy reviews before uploads are enabled. Any future optional diagnostics require your separate opt-in, worldwide. You can use Slipgates without agreeing to them. This is about the optional diagnostic feature, not a claim that normal sign-in, hosting, connection records or information you deliberately share contain no personal or session information.

If optional diagnostics become available, you can refuse them or later turn them off without losing normal functionality. Turning them off stops future optional diagnostic collection/uploads; it does not itself delete records already received. Contact the privacy address about retained information.

Uninstalling and unresolved provider handling

Uninstalling does not itself erase server or support records. The Windows profile, including device keys, settings and logs, also remains locally unless separately removed using the uninstall instructions.

The US invitation scope does not mean all processing stays in the US. The identified Azure regional resources do not establish all provider, transit, endpoint, support or backup locations. Provider access, residual copies and retention/deletion limits identified as unconfirmed above remain unresolved. This website does not make a blanket assurance that its hosting/proxy providers collect no visitor information, set no cookies, use no analytics or involve no other services.
